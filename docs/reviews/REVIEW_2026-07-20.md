## 3. Hallazgos de código NUEVOS (no estaban en la revisión anterior)

Los dos comparten una sola raíz —**el canal de fallo del executor está tipado como
string**— y por eso comparten un solo arreglo limpio.

### 3.1 🟠 El clasificador de infra se puede "envenenar" con contenido del draft

`src/runtime/executor/verdict.ts` aplica el regex `INFRA_FAILURE`
(`ECONNREFUSED|…|quota|rate limit|status code 429|…`) sobre **toda** la cadena
`failure`. Pero esa cadena, en `src/surfaces/commands/regenerate.ts:755`, incluye
`compiled[0].message` — que es `r.message ?? r.reason`, es decir **el diagnóstico
del compilador de TypeScript, que cita el código fuente del draft**
(`out.push({ … message: r.ok ? undefined : r.message ?? r.reason … })`,
`regenerate.ts:381`).

Consecuencia: un draft que **genuinamente no compila** pero cuyo texto de error
contiene un token de infra —p. ej. `error TS2304: Cannot find name
'ECONNREFUSED'`, o un snippet que menciona `rate limit`/`quota`/`429`— se clasifica
como **`infra-error`**, y la policy **termina en el primer intento** en vez de
tratarlo como **`broken`** (que dispararía refine/escalate/extraction-gap). El
dominio del propio proyecto lo hace probable: hay nodos de red y de rate-limit
(adaptador Ollama, dispatcher, `fetch-shim`) cuyos fallos de regen citarían
precisamente esos tokens.

- **Sin test que lo cubra.** `tests/executor-verdict.test.ts` prueba tokens de
  infra como *única* causa (líneas 59–88) y un `broken` limpio *sin* token de
  infra (línea 89). Falta el caso adversarial: un fallo de compilación real cuyo
  diagnóstico *contenga* un token de infra.
- **Arreglo (ver 3.3).** Test adversarial mínimo:
  `"compile-back failed: error TS2304: Cannot find name 'ECONNREFUSED'"` debe
  quedar **`broken`**, no `infra-error`.

### 3.2 🟡 El acoplamiento productor↔clasificador por string no está testeado extremo-a-extremo

La decisión broken-vs-infra depende de que la **redacción exacta** de los
productores siga casando con los regex de `verdict.ts`:

- `regenerate.ts:755` → `` `compile-back failed: …` `` (casa `BROKEN_FAILURE`)
- `regenerate.ts:792` → `"could not read source or regen for comparison"` (casa
  `BROKEN_FAILURE` por el substring `could not read source`)
- `verify/homeomorphism.ts:888` / `:926` → idem.

Los tests **escriben esas cadenas a mano**; ninguno maneja el productor real y
verifica que su salida normalice al outcome esperado. Si alguien reformula un
mensaje de productor (p. ej. `compile-back failed:` → `regeneration did not
compile:`), el verdict pasa **silenciosamente** de `broken` (refinable) a
`infra-error` (terminal) con el suite en verde — exactamente la clase de
mala-clasificación infra-vs-capacity que el equipo ya golpeó **dos veces** el
07-07.

### 3.3 Arreglo recomendado (cierra 3.1 y 3.2 de una)

**Tipar el canal de fallo.** Que la ruta de regen/compile-back emita un
`failureKind: 'transport' | 'compile' | 'oracle' | 'lock' | 'not-found'`
estructurado en vez de fundir el error de transporte y el diagnóstico de TS en
una sola string que el clasificador olfatea con regex. `verdict.ts` rutea por el
enum, no por texto. Beneficios: elimina el envenenamiento (3.1) porque el token de
infra en el diagnóstico de TS ya no importa; elimina el acoplamiento frágil (3.2)
porque no hay redacción que preservar; y es un cambio pequeño y local. Es además
**pre-requisito de B1/B2** (abajo): una corrida nocturna no supervisada tiene que
leer infra-vs-capacidad correctamente sin humano mirando, y hoy esa lectura
depende de coincidencias de string.

## 4. Riesgo de automatización — el `git pull` de esta misma tarea

El `git pull` que pide el guion falló hoy por **lock files stale** que el entorno
**no me deja borrar**:

```
.git/ORIG_HEAD.lock   (Jul 19 03:05 — de la corrida programada de AYER)
.git/index.lock       (Jul 20 03:06 — de mi propio intento de pull)
rm → "Operation not permitted"   (el mount del host bloquea el unlink)
```

Funcionalmente no pasó nada (estamos 0 detrás / 3 delante; nada que traer), pero
**cada corrida diaria va a chocar con esto**: el `pull` aborta en el paso del lock,
y encima deja un lock nuevo que la corrida siguiente hereda. Es un bug de la
automatización, no del proyecto. Opciones:

1. **Cambiar el guion de la tarea** de `git pull` a `git fetch` + chequeo de
   fast-forward (lo que hice hoy): no toca `index.lock`, no deja residuo, y
   reporta igual si hay algo que integrar.
2. Si se quiere un pull real, la tarea debería **limpiar locks stale primero**
   (`find .git -name '*.lock' -mmin +60 -delete`) — pero eso necesita permiso de
   unlink en el mount, que hoy no hay.

Recomendación: opción 1.
