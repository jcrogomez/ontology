# RFC: Walker Interface

**Status:** Walker v1 complete; **v2 early (2026-06-18)** — the node-health
cockpit (`:health`) + governed one-shot controls (`:fichacleanup`, `:reanchor`)
shipped (see §10.1). v0 (Bootstrap 0.4), v1 PR-A (drafts + `:propose`), v1 PR-B
(`:run`), v1 PR-C (`:plan`) all shipped. Full v2 scope (editing + escalation
surfaces) still planned.
**Bootstrap target:** 0.4 (v0 read-only) → 0.6 (full pipeline cockpit)
**Related:** Proposal System (RFC), Run Persistence (RFC)
**Date:** 2026-05-05

## 1. Motivation

Ontology is **terminal-first** by canon. Today the CLI exposes the network through one-shot commands (`inspect`, `node show`, `context assemble`). These are sufficient for scripting but they fragment the experience of *exploring* a typed, temporal, multidimensional graph: each command shows one slice and exits.

The Walker is the focal interactive surface that lets a user navigate the network **without losing context across commands**. It is the editor in **"vim/nano of the future, made to construct itself first, and then to construct any idea generated by intention"**.

The Walker is **the way Ontology authors Ontology**. Without it, authoring at scale is intractable: every node creation requires recalling structure from memory.

### Design principles

1. **Brutalist.** Instant render. No animation, no spinners except for inherently async operations (`:run`, `:compile`).
2. **Fluid.** Every keypress produces immediate visual feedback. The walker should feel as fast as running code, not as an external panel.
3. **Self-bootstrapping.** The walker is the tool that authors the rest of the system, including its own future versions.
4. **Maximally use CLI dimensions.** Color, underline, bold, italic, reverse, box-drawing, and cursor position are all semantic. Nothing decorative.
5. **Honest projection.** The graph is 6-dimensional. The walker projects one focal node at a time and exposes one keystroke per dimension. It never pretends to render all dimensions simultaneously.

### Math alignment

Each visual element in the walker renders a mathematical axiom of the canon:

| Visual element | Math axiom |
|---|---|
| Color of frame and command line | Poset of abstraction (axiom 3) |
| Underlined tokens shared across nodes | Presheaf overlap (axiom 5) |
| Edge list with direction arrows | Typed directed multigraph (axiom 1) |
| Time scrub key | Temporal log (axiom 2) |
| Plane and manifestation rotation | Multidimensional coordinates (canon §6) |
| Pipeline run order | Compiler functor (axiom 6), topology-driven |

A feature that does not render an axiom is out of scope.

## 2. Single-cell focal view

The Walker shows one node at a time. The cell encodes everything needed to understand and act on that node:

```
┌─ node_0042  harvest_record ──────────── domain · semantic · intent ──┐
│                                                                      │
│  Prompt                                                              │
│   When a harvest is recorded, compute stock_delta from               │
│   harvestedQuantity minus seededQuantity and emit a stock event.     │
│   ─────────────                ─────────────────                     │
│                                                                      │
│  Constraints                                                         │
│   • harvest must affect stock                                        │
│   • harvest cannot mutate without approval                           │
│   • seededQuantity ≤ harvestedQuantity                               │
│                                                                      │
│  Requires                       Provides                             │
│   harvest_quantity   shared:3    stock_delta       shared:2          │
│   inventory_state    shared:2    harvest_event     shared:1          │
│                                                                      │
│  Edges                                                               │
│   → validates_against  node_0033  orders                             │
│   → depends_on         node_0001  inventory                          │
│   → emits              node_0099  stock_delta                        │
│   ← documents          node_0021  harvest_doc                        │
│                                                                      │
│  Path                                                                │
│   canon » project » target » stack » domain » harvest_record         │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
 ↑ parent  ↓ child  ← prev  → next  TAB plane  T time  B branch  : cmd
```

Sections, in fixed order: identity bar, prompt, constraints, requires/provides, edges, path, hint bar.

## 3. Color system

The frame border, the level tag (`domain · semantic · intent`), and the path gradient are colored by abstraction level. The 11 levels of the poset map to a hue progression:

| Level | Hue |
|---|---|
| canon | white |
| project | blue |
| target | cyan |
| stack | green |
| architecture | lime |
| domain | yellow |
| workflow | orange |
| interface | magenta |
| unit | red |
| token | dim white |
| artifact | gray |

A user looking at a yellow border knows immediately they are at `domain` level. The path bar is a colored gradient showing the route from canon to the focal node. **No textual chrome is needed to communicate hierarchy.**

The command line at the bottom of the screen takes the same color as the focal node's level.

## 4. Cross-node concept underlining

Tokens that appear in another node's `requires`/`provides`/`prompt` within the focal neighborhood are underlined. The marker `shared:N` next to `Requires` and `Provides` items reports how many distinct nodes share the token.

This is the visual proof of the presheaf gluing: if `harvest_quantity` is underlined here, at least one other node in the local neighborhood provides or requires it. The viewer can press `g` on a shared token to jump to the next node containing it.

The underlining is **read-only**. It does not assert that the gluing succeeds — that is `validateIntent`'s job. It only surfaces overlap. If the gluing fails (a forbidden token appears in two places it shouldn't), `validateIntent` reports the violation through a separate channel.

## 5. Navigation

Two layers: arrow keys for the most-traveled path (poset), supplementary keys for the other coordinate axes.

| Key | Action | Dimension |
|---|---|---|
| ↑ | parent (up the poset) | abstraction |
| ↓ | child (refinement) | abstraction |
| ← | previous sibling | abstraction lateral |
| → | next sibling | abstraction lateral |
| `TAB` | rotate plane (semantic → visual → ...) | plane |
| `T` | enter time scrub mode | time |
| `B` | branch hop | branch |
| `M` | rotate manifestation (intent → ast → osl → ...) | manifestation |
| `E <type>` | walk an outgoing edge of given type | edge |
| `g` | jump to next node sharing the focal token | gluing |
| `:` | command mode (vim-style) | meta |

The hint bar at the bottom shows the most useful keys for the current node. Less-used commands are accessible via `:`.

### Fluidity contract

Arrow navigation must render the next cell within 16ms (one frame) for graphs up to 10,000 nodes. This is enforced by:

- Loading nodes lazily (only the focal node and its 1-hop neighborhood).
- Caching path-to-canon and edge index on first traversal.
- Pre-computing shared-token sets in O(neighborhood) at navigation time.

`T`, `B`, `M`, and `:` may take longer because they may load larger slices, but they must never block the keyboard for more than 100ms without showing a state indicator.

## 6. Modes

The Walker has discrete modes. The mode is shown in the bottom-left of the hint bar.

- **VIEW** (default) — read-only navigation.
- **EDIT** — entered via `i` on a section. The focal section becomes editable. `Esc` saves a draft to `.ontology/work/<nodeId>.draft.json` (not committed). The Walker does not mutate `.ontology` directly; edits become proposals via `:propose`.
- **RUN** — entered via `:run`. Dispatches a model run for the focal node, shows the response inline as a candidate, and offers `:propose` to convert the response into a proposal.
- **SCRUB** — entered via `T`. Bottom hint bar becomes a time slider; arrows move time, `Enter` snaps. The view re-renders the cell as it was at that time.
- **COMMAND** — entered via `:`. Vim-style command line.

## 7. Pipeline cockpit

The Walker is the cockpit for the four-stage authoring pipeline:

```
edit → run → postprocess → compile
```

Stages:

1. **Edit** — `i` on the focal node's prompt. Saves a draft locally.
2. **Run** — `:run` dispatches the LLM with the assembled context. Output is shown as a candidate inline.
3. **Postprocess** — `:propose` validates the candidate via `validateIntent` and the presheaf gluing, then writes a proposal file.
4. **Compile** — `:compile` traverses the network in topology-determined order and emits artifacts.

### Topology-driven compilation

The compile order is **not fixed**. It is computed at compile time from the graph itself:

| Edge type | Compile semantics |
|---|---|
| `inherits_from`, `depends_on`, `refines`, `implements`, `uses_token` | Hard ordering (target compiles after source) |
| `validates_against` | Validation pass, parallel to main pass |
| `documents`, `tests` | Post-pass (after main artifacts emit) |
| `mutates`, `reads_from`, `emits`, `triggers`, `belongs_to`, `orbits` | Runtime relationships, no compile-order implication |
| `contradicts` | Hard fail; halt with conflict report |
| `supersedes` | Predecessor is excluded from compile |
| `blocks` / `unblocks` | Gating relationships (target excluded while blocker is unresolved) |

Plus the poset constraint: nodes at higher abstraction compile before lower (canon → project → ... → artifact). And the time/branch filters: only nodes on the active branch and at or before the active time are included.

**The user shapes the pipeline by shaping the graph.** Adding an edge changes compile order. Removing one re-parallelizes. Changing a node's level moves it earlier or later in the poset pass. The pipeline topology *is* the graph.

CLI:

- `:compile --plan` — print the topological plan without executing.
- `:compile --dry-run` — run the LLM phase but do not write artifacts.
- `:compile` — execute the plan and write artifacts.

The plan is content-addressed. Re-running with the same graph state produces the same plan hash, enabling deterministic CI replays.

## 8. v0 scope

Walker v0 is **read-only** and ships with:

- Single-cell focal view.
- Color by poset level.
- Underline cross-node tokens (substring match within local neighborhood).
- Arrow nav, `TAB`, `T` (read-only scrub), `B` (read-only branch hop), `:q`, `:help`.
- No edit mode, no run mode, no proposals, no compile.

This is enough to dogfood every subsequent feature.

## 9. v1 scope

Walker v1 ships in three slices:

**PR-A (this slice):**
- Edit mode (`i` enters, `Esc` saves) backed by drafts under `.ontology/work/drafts/<focalId>.draft.json`.
- A "(draft pending)" indicator on the identity bar when the focal has a saved draft.
- `:propose` creates a `node_create` proposal as a child of the focal (level + kind inherited; payload.prompt = the draft text). The draft is cleared on success; the proposal carries its content forward.
- `:cleardraft` removes a saved draft.
- The walker never mutates the network directly. `:propose` produces a proposal that the user later applies via `onto proposal apply`.

**PR-B (this slice):**
- `:run` (default `mock`) and `:run ollama` dispatch a model run against the focal node's assembled context.
- The walker stays interactive while the dispatch is in flight: a "running" panel renders synchronously, then the result panel replaces it on resolve.
- Persistence is always on. Each `:run` produces a content-addressed record under `.ontology/runs/run_<id>.json` and emits a `run_persisted` event. Re-running with identical inputs surfaces the same id with a `(cached)` flag; no second dispatch fires.
- `:clearrun` dismisses the result panel without affecting the persisted record.

**PR-C (this slice):**
- `:plan` computes the topological compile plan rooted at the focal: dependency closure, sequenced via Kahn's algorithm over the hard-dependency edge family (`depends_on`, `inherits_from`, `refines`, `implements`, `uses_token`).
- The walker renders a green panel listing each step with its node id and the count of dependency edges resolved at that step. The focal is marked `*`. A cycle in the closure renders the panel in red with the unresolved set.
- `:clearplan` dismisses the panel.
- The same helper backs `onto compile plan <nodeId> [--json]` so scripts and the TUI agree on the order.
- Read-only. The actual compiler ships in Bootstrap 0.8.

**v1.5 (2026-06-09) — the three scope gaps closed:**
- `:propose-update` — the draft becomes a **`node_update` proposal on the focal itself** (in-place refinement; `:propose` keeps creating a child). Pinned to the focal's hash, applied via `:proposals` or the CLI — the two-step mutation discipline is unchanged.
- `:verify` — the focal's round-trip verdict (dual distances + five-label fold, same primitives as `onto verify-homeomorphism`) computed **against the last compiled artifact**, pure and synchronous — no dispatch. Honest scope: a stale artifact gives a stale verdict (`:compile` first); the full sweep (regen, reps, matrix, behaviour axis) stays on the CLI.
- `:workflow <graph> --input <file> [provider] [--model X] [--propose-update]` — run a Phase ζ workflow graph from the TUI (async, same two-stage pattern as `:run`). With `--propose-update`, an ACCEPTED run goes through the exact §3.6 provenance path the CLI uses: a `wfrun_*` record is persisted first, then a `node_update` proposal on the focal (plus `edge_create` proposals for graph-declared edges, listed in apply order).

**v1.6 (2026-06-10) — intent-first editing loop, slice 1.** The walker's
target shape is THE primary editing layer over intentions, with the compiled
artifact in sight, never as the editing surface. This slice lands the window
and the inverse direction:

- `a` / `:preview` — toggle the **artifact preview panel**: the first ~18
  lines of the focal's shadow (`outputs.files[0]`), read-only, with a shadow
  badge against the last `onto drift --update` anchor (`✓ matches anchor`,
  `≠ DRIFTED`, `? missing`, or `no anchor` when none exists). `:clearpreview`
  closes it. The panel never edits the file.
- `:which <file>` — **inverse traceability**: jumps the focal to the node
  whose `outputs.files` contains the path (absolute or cwd-relative) and
  opens the preview. Multiple owners are reported; no owner is a clear
  message, not an error.
- **Shadow glyph on the identity bar** — `≠ shadow drifted` (yellow) or
  `? shadow missing` (red) next to the focal id when its artifact diverges
  from the drift anchor. Clean/no-anchor states stay silent. Recompiling is
  ALWAYS manual (`:compile`) — drift is surfaced, never acted on
  automatically.
- Implementation: `src/surfaces/walker/state/shadow-status.ts` (status + preview +
  owner lookup, reusing the merkle hash + drift snapshot),
  `src/surfaces/walker/layout/artifact-preview-panel.tsx`. Pinned by
  `tests/walker-artifact-preview.test.tsx` (stdin-driven flows).

### v1.x — `:graph view [depth]` (post-0.9)

A read-only walker action that renders the focal node's k-hop subgraph
as a structured panel, sharing the same `extractSubgraph` helper that
backs `onto graph subgraph`. The default depth is 2; `:graph view 3`
expands further (capped at 5 — beyond that the panel becomes a hairball
that defeats inspection).

The render is *structural*, not pictorial: no boxes-and-lines ASCII
art. Three buckets — **Upstream** (`↑`, nodes reachable from the focal
via incoming edges), **Downstream** (`↓`, outgoing), and **Lateral**
(`↔`, slice members reachable from neither direction) — each lists its
nodes with the focal-relative arrow, the abstraction-level color
matching `POSET_COLORS`, the `kind/abstraction` tag dimmed, and the
truncated label. A second dimmed line per row enumerates up to 4
incident edges (`→ depends_on node_X`-style). Buckets cap at 15 rows
each; a `…N more node(s) hidden` hint appears when the slice is
larger.

Deterministic — two runs over the same `.ontology/` produce
byte-identical output. Implemented by
`src/surfaces/walker/actions/graph-view-from-walker.ts`; the parser lives at
`src/surfaces/walker/state/parse-graph-view-args.ts`. This is the terminal-first
answer to the "Visual DAG Studio" follow-up — keeps the project to a
single surface (Ink/TUI) and avoids forking into a web codebase.
Dismiss with `:clearinfo`.

### v1.x — `:link-analysis` (post-0.9)

A read-only walker action that mirrors `onto link <nodeId>` from inside
the TUI. Wraps `semanticLink()` with the focal cell as target and the
focal's own `prompt.raw` as the default candidate (the question becomes
*"does my own prompt satisfy my context contract?"*). Renders into the
unified info panel (yellow border when there are missing requirements,
red when validation fails outright, green when clean). Sections:
validation summary, requires (with provider attribution), provides,
forbids (with violators), and a list of edge proposal suggestions. Each
suggestion is a copy-pasteable `onto propose link …` command — the
walker never auto-creates proposals. Read-only; dismiss with
`:clearinfo`. Helper: `src/surfaces/walker/actions/link-analysis-from-walker.ts`,
shared with the CLI via `src/forward/context/edge-suggester.ts`.

## 10. v2 scope

### 10.1 v2 early — shipped 2026-06-18

The governed-loop cockpit, focal-node first:

- **`:health`** (alias `:status`) — the node-health dashboard for the focal
  node: identity, code-shadow freshness, behaviour-fixture + static-rule
  coverage, ficha quality, dependency closure (upstream/dependents), and the
  ranked **next safe action** (what + why + the command). Colour-coded by
  confidence (syncable=green / lower=yellow / blocked=red). Pure read-only
  composition (`actions/node-health-from-walker.ts`); the same readiness
  `onto status --blockers` computes at the graph level.
- **`:fichacleanup`** — one-shot control: run the deterministic ficha
  reconciliation (complete missing exports + prune phantom provides) on the
  focal, governed via `updateNode`, then refresh `:health`.
- **`:reanchor`** — one-shot control: refresh THIS node's drift anchor (accept
  the current shadow as baseline), then refresh `:health`.

Both controls reuse the shared cores in `commands/ficha.ts` /
`laws/reanchor-node.ts` (one implementation of the delicate mutation) and bump
the reload tick so the focal's derived state recomputes immediately. The
remaining v2 surfaces (editing with contract diff, escalation surface) are below.

### 10.2 v2 scope (planned)

Walker v2:

- Full pipeline cockpit, including `:compile`.
- Proposal review pane (renders pending proposals as candidate cells in the neighborhood).
- Edge-walk (`E <type>`).
- Manifestation rotation (`M`) once `ast`, `osl`, `code` manifestations exist.

## 11. Out of scope

- Mouse interaction.
- Web UI / Visual DAG Studio (separate project, much later, would project the walker into 2D).
- Multi-cell layout. The view is monoscopic by design.
- Animation. The Walker is brutalist — instant render, no transitions.

## 12. Open questions

1. Should the underline matching be exact-token (whitespace-bounded) or semantic (case-insensitive, plural-stripped)? v0 ships exact-token; v2 may add semantic with explicit user opt-in.
2. Where does `:run`'s candidate output live before `:propose`? Probably `.ontology/work/<nodeId>.candidate.json`, ephemeral.
3. How does the Walker handle terminals narrower than the cell width? Either word-wrap with continuation marker, or refuse to render below a threshold. Open.
4. Should `:compile --plan` render its output as a sequence of focal cells (animated by step) or as a static topological list? The brutalist principle leans static; the fluidity principle leans animated. Open.
